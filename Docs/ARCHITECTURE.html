Pica · Pipecat voice client · Android

The phone is just a mic and a speaker. The server is the brain.

Pica is a thin Android voice client for Pipecat. You speak; a Pipecat server does all the work — STT, LLM, TTS, turn detection, barge-in — and streams audio back over a direct peer-to-peer WebRTC link. No JWT, no SFU, no rooms: signaling is literally POST an SDP offer to /api/offer.

Signal path

One WebRTC link, two directions, one side channel

Audio flows peer-to-peer as Opus in both directions. The same link carries RTVI events — a control side channel that drives the chat, the latency HUD and the agent's chosen visualizer. Everything between the two Opus streams lives on the server; the app never knows what's in there.

Module map

Where each responsibility lives. The whole vendor SDK sits in net/PicaVoiceClient.kt — the recent 0.3.x → 1.1.0 jump touched only that file.

PicaVoiceClient.kt the only SDK file

Wraps PipecatClient + SmallWebRTCTransport. Translates PipecatEventCallbacks into the app's transport-agnostic Listener. connect() POSTs the SDP offer to the agent's URL verbatim.

VoiceAgentViewModel.kt session brain

Owns the session across config changes. Implements Listener; maps RTVI events to AgentUiState, transcript persistence, orb amplitude, and the latency HUD. Manages the agent list, selection, and speaker routing.

MainActivity.kt compose host

Switches between three states: live session, read-only history viewer, idle setup+drawer. Owns the app-root snackbar, permission requests, keep-screen-on, and the mic foreground service.

ServerEndpoint.kt the "agent"

One selectable backend: host, port, path, scheme, label, accent, and a visualizer key (stored as a string so unknown future keys degrade to the default). url/badge derived. InitialAgents seeds three from BuildConfig, then they're editable rows.

PicaSessionHost.kt session driver

DisposableEffect: connect() on enter, disconnect() on dispose. Composed only while the session is active — almost nothing here, by design.

MicForegroundService.kt foreground svc

Holds the MICROPHONE foreground type so a session survives the screen turning off. Captures no audio itself — libwebrtc owns the mic; this just keeps the process promoted.

data/ · repo/ persistence

Room: ChatSession (with an agent snapshot) + MessageItem. ConversationRepository upserts incremental transcripts, streams saved sessions, and purges unsaved ones at startup.

VisualizerStyle.kt · ui visualizers visualizers

Enum of per-agent session visualizers — SCOPE, BASES, ORB — picked in the agent editor and switched on in VoiceAgentScreen (the single branch point). Rendered by ScopeVisualizer / BasesVisualizer / OrbVisualizer.

ui/ · di/ · prefs/ supporting

Setup, VoiceAgent, drawer + viewer screens; ServiceLocator (repo + AudioManager); PicaLocalPrefs (agent list + selection + speaker pref as JSON).

Runtime

Session lifecycle

A real sequence — each step is a genuine handoff between the UI, the ViewModel, the SDK wrapper and the server.

1

Start

startSession() creates a Room session row (with an agent snapshot), registers an AudioDeviceCallback for hot-plug routing, flips sessionActive=true. MainActivity requests mic (+ notification) permission, starts the foreground service, keeps the screen on.

2

Connect

PicaSessionHost composes and calls connect(). A fresh PicaVoiceClient bound to the selected agent's URL POSTs the SDP offer; the server answers; ICE completes; media flows P2P.

3

Bot speaks first

The server seeds a greeting on on_client_connected, so you hear Pica before saying anything — confirming the loop is alive end to end.

4

Converse

libwebrtc captures the mic (AEC3), encodes Opus, ships it up. RTVI events map to UI: speaking → visualizer tint + latency stopwatch; transcripts → chat bubbles, persisted to Room incrementally.

5

Barge-in

Local playback stops the instant you speak (onUserStartedSpeaking), before the server's VAD interrupt even round-trips. The server's interruption catches up.

6

Stop

onDispose → disconnect() fully tears the client down (disconnect + release). stopSession() resets audio mode, unregisters the device callback, discards the session if unsaved, stops the foreground service. Only one backend is ever live at a time.

Client ⇄ server

The whole contract

As long as these hold, the server's internal pipeline wiring can change freely.

POST  /api/offer — the only HTTP endpoint. One offer per session.

// request  (application/json)
{ "sdp": "<offer sdp>",
  "type": "offer",
  "pc_id": "<optional>" }

// response 200
{ "sdp": "<answer sdp>",
  "type": "answer",
  "pc_id": "<connection id>" }

Produced/consumed by Pipecat's SmallWebRTCRequestHandler (server) and SmallWebRTCTransport (client) — don't hand-roll it. After the answer, ICE completes and media flows P2P.

What the server must do:

  • Answer /api/offer and return the handler's answer verbatim.
  • Run an RTVIProcessor + RTVIObserver so the app gets speaking / transcript events.
  • Enable VAD + interruptions for barge-in.
  • Seed a greeting on on_client_connected — the bot speaks first.
AEC3 on both ends. Echo cancellation is built into libwebrtc on client and server. Do not disable it — without it, the bot transcribes itself.
Not in v1: voice selection. The app sends no voice ID; the server uses its configured Cartesia voice. Runtime switching needs an RTVI custom message on both ends.
Configuration

The "agent" model — a backend is just data

Every agent speaks the identical WebRTC+RTVI contract, so the only thing that differs is the offer URL the transport POSTs to — plus cosmetics: a label, an accent color, and a per-agent visualizer. Adding a backend is adding a row — no code. Two ship seeded from build config; after first launch they're ordinary editable/deletable rows.

id · openclaw
OpenClaw

OPENCLAW_SERVER_URL — the agentic backend, the conference demo. The default selection.

id · direct
Direct

PICA_SERVER_URL — the straight Pipecat voice loop.

Both URLs are required by the build — build.gradle.kts fails fast if either is missing. Each is the full offer endpoint the transport POSTs to verbatim; the seeds are not recomputed from build config on later launches.

Session UI

Visualizers — a per-agent choice

Each agent picks its own session visualizer in the agent editor (a radio list that enumerates VisualizerStyle.entries). The choice is persisted on the agent as a plain string key, so an unknown future key degrades to the default instead of failing to deserialize. VoiceAgentScreen is the single branch point that composes the chosen style.

key · scope · default
Oscilloscope

ScopeVisualizer.kt — phosphor-scope trace, terminal green for the bot, cyan for the user, pulsing with speech cadence. Agents persisted before the feature resolve to it.

key · bases
Running the Bases

BasesVisualizer.kt — Dodger-blue ballpark. A glowing runner sprints the bases while someone speaks, holds the nearest bag in silence, and scores runs on a scoreboard pill. Runner tint follows the speaker.

key · orb
Orange Orb

OrbVisualizer.kt — the Cliff sibling app's additive amber/bronze orb stack; breathing, spread, spin and wobble track speech, with a warm/cool center bloom per speaker.

All three run on the same synthesized speech envelope (level + speechPulse + activeSource) — the transport delivers no real audio levels. Adding a style is one VisualizerStyle entry plus one branch in VoiceAgentScreen; the editor's picker needs no change.

The headline number

Latency HUD

A number you can defend on stage — measured purely client-side, so it's the user-perceived responsiveness, not a server-reported metric.

onUserStoppedSpeaking→onBotStartedSpeaking

Silence → first bot audio, per turn, via monotonic SystemClock.elapsedRealtime(). The server doesn't send this — the client owns the truth. Keeping enable_metrics=True server-side lets the turn-detect / LLM TTFB / TTS TTFB breakdown line up for cross-checking.

Sharp edges

Known quirks

  • No client-side audio levels. The SmallWebRTC RTVI client never emits amplitude, so all three visualizers are event-driven — they animate on a synthesized envelope (speechPulse on transcript tokens + speaking start/stop) rather than true amplitude. The level hooks are wired but stay at 0.
  • Voice selection is server-side in v1. The app sends no voice ID; switching would need an RTVI custom message on both ends.
  • onBotTranscript is deprecated in the 1.x SDK (in favor of onBotOutput) but still fires; migrating is a follow-up, not part of the version bump.
